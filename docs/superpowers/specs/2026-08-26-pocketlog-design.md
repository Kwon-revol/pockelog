# PockeLog 제품 및 시스템 설계

- 문서 상태: 사용자 승인 완료 설계안
- 작성일: 2026-08-26
- 대상 릴리스: 첫 공개 가능한 웹/PWA 버전
- 기본 시간대: Asia/Seoul
- 기본 통화: KRW

## 1. 목적

PockeLog는 한 사람이 개인 장부를 관리하거나 소수 사용자가 공동 장부를 함께 기록할 수 있는 가계부다. 휴대폰에서는 설치 가능한 웹 앱처럼 빠르게 거래를 입력하고, PC에서는 넓은 화면으로 거래 목록과 통계를 확인한다.

첫 버전의 핵심 가치는 다음과 같다.

1. 수입과 지출을 적은 입력만으로 빠르게 기록한다.
2. 사용자와 장부 단위로 데이터를 안전하게 격리한다.
3. 달력 월뿐 아니라 사용자가 정한 정산 기준일에 따라 통계를 계산한다.
4. 공동 장부에서도 입력자를 구분하고 역할에 맞는 수정 권한을 보장한다.
5. 자동 세무 판단 없이 사용자가 절세 목표와 납입 현황을 관리한다.

## 2. 성공 기준

첫 버전은 다음 조건을 모두 만족하면 성공으로 본다.

- 사용자가 아이디, 비밀번호, 사용자명, 이메일, 전화번호로 가입할 수 있다.
- 가입 직후 개인 장부와 기본 분류가 자동 생성된다.
- 사용자는 아이디 또는 이메일과 비밀번호로 로그인할 수 있다.
- 개인 장부의 데이터는 다른 사용자에게 노출되지 않는다.
- 공동 장부 소유자는 모든 거래를 관리하고 참여자는 자신이 입력한 거래만 수정하거나 삭제할 수 있다.
- 모바일과 PC에서 동일한 데이터와 기능을 사용할 수 있다.
- 선택 기간 및 장부 정산 기간의 수입, 지출, 차액이 정확히 계산된다.
- 기간별·분류별 통계와 원본 거래 목록이 서로 일치한다.
- 사용자는 개인 절세 목표와 납입 내역을 연도별로 관리할 수 있다.
- Vercel 운영 배포와 Supabase 운영 데이터베이스가 GitHub 저장소의 코드 및 마이그레이션으로 재현 가능하다.

## 4. 기술 구조

### 4.1 구성

- 프레임워크: Next.js App Router, React, TypeScript
- 스타일: Tailwind CSS 기반 디자인 토큰과 재사용 UI 컴포넌트
- 호스팅: GitHub와 연결된 Vercel
- 인증: Supabase Auth 이메일·비밀번호 인증
- 데이터베이스: Supabase Postgres
- 권한: Postgres grants와 Row Level Security 정책
- PWA: 웹 앱 매니페스트, 설치 아이콘, 앱 셸 캐시
- DB 변경 관리: 저장소의 Supabase SQL 마이그레이션

Next.js는 화면 렌더링과 서버 전용 작업을 한 프로젝트에서 담당한다. 일반 데이터 접근은 로그인 사용자의 Supabase 세션으로 수행하여 RLS를 항상 통과시킨다. 아이디 로그인 식별자 조회와 초대 대상 조회처럼 비공개 식별자에 접근하는 작업만 서버 전용 모듈이 수행한다.

### 4.2 모듈 경계

애플리케이션은 다음 모듈로 나눈다.

- `auth`: 가입, 로그인, 세션, 비밀번호 재설정, 인증 콜백
- `profiles`: 공개 표시 이름과 비공개 연락처
- `ledgers`: 개인·공동 장부와 장부 선택
- `memberships`: 초대, 수락, 역할, 참여자 관리
- `categories`: 장부별 수입·지출 분류
- `transactions`: 거래 CRUD, 검색, 휴지통, CSV
- `statistics`: 기간 계산, 요약, 분류별 집계
- `tax-goals`: 개인 절세 목표와 납입 내역
- `settings`: 프로필, 장부, 기준일, 분류 설정
- `shared`: 날짜, 금액, 검증, 공통 UI처럼 도메인에 종속되지 않는 코드

각 모듈은 화면 컴포넌트, 입력 스키마, 데이터 접근 함수, 도메인 계산을 분리한다. 서버 전용 코드에는 명확한 server-only 경계를 두고 브라우저 번들에서 가져올 수 없게 한다.

### 4.3 배포 환경

- 로컬 개발은 로컬 Supabase 환경을 우선 사용한다.
- Vercel Preview는 운영과 분리된 Supabase 개발 프로젝트를 사용한다.
- Vercel Production은 Supabase 운영 프로젝트만 사용한다.
- 마이그레이션은 개발 환경에서 검증한 뒤 운영 환경에 적용한다.
- 운영 데이터베이스를 개발 또는 E2E 테스트 대상으로 사용하지 않는다.

필수 환경변수는 다음과 같다.

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- `SUPABASE_SECRET_KEY`
- `NEXT_PUBLIC_APP_URL`

서비스 역할 키는 아이디 로그인 식별자 조회와 초대 대상 조회 같은 제한된 서버 전용 함수에서만 사용한다. 일반 거래 및 통계 요청에는 사용하지 않는다.

## 5. 인증과 계정

### 5.1 회원가입 입력

- 아이디: 4~20자, 영문 소문자·숫자·밑줄만 허용, 대소문자 구분 없이 고유
- 비밀번호: 최소 8자, 비밀번호 확인 필수
- 사용자명: 1~30자, 앞뒤 공백 제거
- 이메일: 형식 검증, 대소문자 구분 없이 고유
- 전화번호: 숫자와 하이픈 입력 허용, 저장 전 숫자만 남겨 정규화

전화번호는 인증이나 중복 가입 차단에 사용하지 않는다. 본인 프로필 화면 외에는 노출하지 않는다.
아이디와 가입 이메일 변경은 첫 버전에서 제공하지 않는다. 사용자명, 전화번호, 비밀번호만 설정에서 변경할 수 있다.

### 5.2 가입 처리

가입 서버 작업은 입력을 검증한 뒤 Supabase Auth에 이메일과 비밀번호를 등록한다. 아이디, 사용자명, 정규화한 전화번호는 가입 메타데이터로 함께 전달한다. `auth.users` 생성 트리거는 동일한 데이터베이스 트랜잭션 안에서 다음 작업을 수행한다.

1. 비공개 로그인 식별자 생성
2. 공개 프로필과 비공개 프로필 생성
3. 사용자 소유의 `내 장부` 생성
4. 사용자를 해당 장부의 소유자로 등록
5. 기본 수입·지출 분류 생성
6. 기본 장부를 사용자 환경설정에 기록

아이디나 이메일 고유성 위반 시 전체 가입을 실패시키며 부분 프로필이나 장부를 남기지 않는다.

### 5.3 로그인

로그인 입력 하나에서 아이디 또는 이메일을 받는다.

- 이메일 형식이면 정규화한 이메일을 사용한다.
- 아이디 형식이면 서버가 비공개 로그인 식별자 테이블에서 연결된 이메일을 찾는다.
- 이후 표준 Supabase `signInWithPassword` 흐름으로 세션을 생성한다.
- 성공한 세션은 Next.js 서버와 브라우저가 함께 사용할 수 있는 쿠키에 보관하고 갱신한다.
- 존재하지 않는 계정, 잘못된 비밀번호, 비활성 계정은 모두 같은 사용자 메시지를 반환한다.

아이디와 이메일의 존재 여부, 내부 사용자 UUID, 원래 이메일은 오류 응답이나 로그에 포함하지 않는다.

### 5.4 이메일 확인과 비밀번호 재설정

첫 운영 배포에서는 Supabase의 가입 이메일 확인 필수 설정을 끈다. `/auth/callback`과 확인 완료·실패 화면은 구현하여 나중에 설정만 켜도 신규 가입 흐름이 작동하게 한다. 확인 필수 설정을 나중에 켜면 기존 계정은 그대로 로그인할 수 있고, 활성화 이후 신규 가입자부터 확인을 요구한다.

비밀번호 재설정은 가입 이메일로 링크를 보내는 Supabase 흐름을 사용한다. 운영에서 확인 메일과 재설정 메일을 실제 발송하려면 Supabase에 별도의 SMTP 발송 설정이 필요하다. SMTP가 구성되지 않은 환경에서는 개발용 메일 캡처 또는 허용된 테스트 주소로만 검증한다.

## 6. 데이터 모델

모든 기본 키는 UUID를 사용한다. 금액은 원화 정수 `bigint`로 저장하고 0보다 커야 한다. 생성·수정 시각은 UTC `timestamptz`, 사용자가 선택하는 거래일과 납입일은 `date`로 저장한다.

### 6.1 사용자 데이터

#### `public.profiles`

- `id`: `auth.users.id`와 동일한 사용자 ID
- `display_name`: 공동 장부에 표시할 사용자명
- `created_at`, `updated_at`

공동 장부 구성원은 서로의 표시 이름만 볼 수 있다.

#### `public.user_private_profiles`

- `user_id`
- `phone_normalized`
- `default_ledger_id`
- `created_at`, `updated_at`

본인만 조회하고 수정할 수 있다.

#### `private.account_identifiers`

- `user_id`
- `login_id`
- `email_normalized`
- `created_at`, `updated_at`

비공개 스키마에 두며 Data API로 노출하지 않는다. 로그인과 초대 대상 조회 서버 함수만 접근한다.

### 6.2 장부와 구성원

#### `public.ledgers`

- `id`
- `owner_id`
- `kind`: `personal` 또는 `shared`
- `name`
- `currency_code`: 첫 버전에서는 `KRW`
- `period_start_day`: 1~28, `null`이면 말일
- `created_at`, `updated_at`

사용자당 개인 장부는 하나만 자동 생성한다. 추가 장부는 공동 장부로 생성한다. 개인 장부에는 다른 사용자를 초대할 수 없다.

#### `public.ledger_members`

- `ledger_id`
- `user_id`
- `role`: `owner` 또는 `member`
- `joined_at`

장부에는 정확히 한 명의 소유자가 존재하며 `ledgers.owner_id`와 소유자 구성원 행이 일치해야 한다.

#### `public.ledger_invitations`

- `id`
- `ledger_id`
- `target_user_id`
- `invited_by`
- `status`: `pending`, `accepted`, `declined`, `revoked`, `expired`
- `expires_at`: 생성 시점부터 7일
- `created_at`, `responded_at`

소유자가 아이디 또는 이메일을 입력하면 서버에서 기존 사용자를 찾고 초대를 만든다. 첫 버전은 미가입자에게 외부 이메일을 보내지 않는다. 초대 대상은 로그인 후 앱 안에서 수락하거나 거절한다. 같은 장부와 대상에 활성 초대는 하나만 허용한다.

### 6.3 분류와 거래

#### `public.categories`

- `id`
- `ledger_id`
- `type`: `income` 또는 `expense`
- `name`
- `color`
- `sort_order`
- `is_active`
- `created_at`, `updated_at`

장부, 유형, 이름 조합은 대소문자 구분 없이 고유하다. 거래가 참조한 분류는 삭제하지 않고 비활성화한다. 비활성 분류는 신규 입력 선택지에서 숨기지만 기존 거래와 통계에는 표시한다.

기본 지출 분류는 식비, 교통, 주거·공과금, 생활, 건강·의료, 쇼핑, 취미·여가, 교육, 경조·선물, 기타다. 기본 수입 분류는 급여, 부수입, 용돈, 환급, 기타다.

#### `public.transactions`

- `id`
- `ledger_id`
- `type`: `income` 또는 `expense`
- `occurred_on`
- `description`
- `amount`
- `category_id`
- `memo`: 선택 입력
- `created_by`
- `idempotency_key`: 클라이언트 저장 시도별 UUID
- `created_at`, `updated_at`
- `deleted_at`, `deleted_by`: 휴지통 상태

장부와 `idempotency_key` 조합을 고유하게 하여 네트워크 재시도로 같은 거래가 중복 등록되는 것을 막는다. 거래 유형과 분류 유형, 거래 장부와 분류 장부가 일치하는지 데이터베이스에서도 검증한다.

휴지통 이동은 `deleted_at`과 `deleted_by`를 기록하는 수정 작업이다. 휴지통 거래는 일반 목록과 모든 통계에서 제외한다. 자동 영구 삭제는 하지 않으며 장부 소유자가 명시적으로 영구 삭제하거나 복원한다.

### 6.4 절세 목표

#### `public.tax_goals`

- `id`
- `user_id`
- `year`
- `name`
- `target_amount`
- `memo`
- `sort_order`
- `created_at`, `updated_at`

#### `public.tax_contributions`

- `id`
- `tax_goal_id`
- `user_id`
- `contributed_on`
- `amount`
- `memo`
- `created_at`, `updated_at`

절세 데이터는 사용자 개인 소유이며 장부 구성원 관계와 무관하다. 법정 한도나 세액을 저장된 기본값으로 제공하지 않는다.

## 7. 권한 모델

모든 노출 테이블에서 RLS를 활성화하고 `anon` 권한을 제거한다. 각 작업은 별도 정책으로 작성한다.

| 자원 | 본인/구성원 | 장부 소유자 | 일반 참여자 |
|---|---|---|---|
| 본인 비공개 프로필 | 본인만 조회·수정 | 해당 없음 | 해당 없음 |
| 장부 | 활성 구성원 조회 | 이름·기준일 수정 | 조회만 가능 |
| 구성원 | 활성 구성원 조회 | 초대·제거 관리 | 본인 나가기 |
| 분류 | 활성 구성원 조회 | 생성·수정·비활성화 | 조회만 가능 |
| 일반 거래 | 활성 구성원 전체 조회 | 모든 거래 수정·휴지통 이동 | 본인 거래만 수정·휴지통 이동 |
| 휴지통 거래 | 소유자만 조회 | 복원·영구 삭제 | 접근 불가 |
| CSV | 해당 없음 | 선택 기간 전체 내보내기 | 내보내기 불가 |
| 절세 목표·납입 | 본인만 전체 관리 | 해당 없음 | 해당 없음 |

참여자가 공동 장부에서 나가면 즉시 장부와 거래 조회 권한을 잃는다. 참여자가 작성한 기존 거래는 장부 기록으로 남고 입력자 표시도 유지한다. 소유자는 자신을 제거하거나 공동 장부에서 나갈 수 없다. 첫 버전에서는 소유권 이전을 제공하지 않으므로 공동 장부를 없애려면 소유자가 장부를 삭제해야 한다.

## 8. 화면과 라우팅

### 8.1 인증 화면

- `/login`: 아이디 또는 이메일, 비밀번호, 비밀번호 찾기
- `/signup`: 회원가입 필드와 약식 개인정보 안내
- `/forgot-password`: 이메일 입력과 발송 결과 안내
- `/reset-password`: 새 비밀번호 설정
- `/auth/callback`: 확인 및 재설정 코드 교환

### 8.2 로그인 후 공통 셸

- 모바일: 상단 장부 선택기와 하단 `가계부`, `통계`, `세금`, `설정` 탭
- PC: 좌측 사이드 메뉴, 상단 장부 선택기, 중앙 콘텐츠 영역
- 현재 장부가 유효하지 않으면 기본 개인 장부로 이동
- 공동 장부에서는 구성원 요약과 각 거래의 입력자 표시

### 8.3 가계부 탭

기본 경로는 `/ledger`다.

상단에는 조회 기간과 총수입, 총지출, 차액 카드를 표시한다. 기본 조회 범위는 현재 장부 정산 기간이며 사용자가 시작일과 종료일을 직접 선택할 수 있다.

목록 위에는 다음 도구를 둔다.

- 내용과 메모 검색
- 수입·지출 유형 필터
- 분류 필터
- 입력자 필터
- 최신순·오래된순 정렬

거래 목록은 거래일별로 묶는다. 모바일은 카드 목록, PC는 표를 기본 표현으로 사용한다. 거래 추가·수정 폼에는 유형, 거래일, 내용, 분류, 금액, 선택 메모를 둔다. 생성 시각과 입력자는 자동 기록한다.

목록 조회는 한 번에 50건을 가져오는 커서 기반 페이지네이션을 사용한다. 검색과 필터를 변경하면 첫 페이지부터 다시 조회한다.

모바일에서는 고정 추가 버튼으로 폼을 열고, PC에서는 상단 추가 버튼과 우측 패널을 사용한다. 저장 성공 후 목록과 요약을 갱신하고 폼을 닫는다.

### 8.4 통계 탭

기본 경로는 `/statistics`다.

정산 기간 카드마다 수입, 지출, 차액과 수입·지출 비교 막대를 표시한다. 두 막대는 해당 카드의 수입과 지출 중 큰 금액을 100% 길이로 삼아 비교한다. 둘 다 0원이면 빈 막대와 `기록 없음`을 표시한다.

처음에는 현재 정산 기간과 이전 11개 기간을 보여주며, 더 보기로 과거 12개 기간씩 추가한다.

기간 카드를 선택하면 `/statistics/[period-key]` 상세 화면으로 이동한다.

- 기본 상태는 지출 분류 통계
- 수입/지출 전환 제공
- 분류별 금액과 전체 유형 합계 대비 비율 막대 표시
- 비율 내림차순 정렬, 같은 비율이면 분류 정렬 순서 사용
- 아래에 해당 기간과 유형의 원본 거래 목록 표시

### 8.5 세금 탭

기본 경로는 `/tax-goals`다.

연도 선택 후 목표 카드를 표시한다. 카드에는 항목명, 목표 금액, 납입 합계, 남은 금액, 진행률, 메모가 포함된다. 사용자는 목표를 만들고 납입 내역을 날짜별로 추가한다. 진행률 막대는 100%에서 시각적으로 멈추고 초과 금액은 별도로 표시한다.

화면에는 `입력한 목표를 관리하는 도구이며 세무 자문이나 자동 세액 계산이 아니다`라는 안내를 지속적으로 표시한다.

### 8.6 설정 탭

기본 경로는 `/settings`다.

- 프로필: 사용자명, 전화번호, 비밀번호 변경
- 장부: 생성, 이름 변경, 장부 선택, 공동 장부 삭제
- 공동 사용자: 초대, 초대 수락·거절, 참여자 제거, 나가기
- 정산 기간: 시작일 1~28 또는 말일
- 분류: 수입·지출 분류 생성, 이름·색상·순서 변경, 비활성화
- 데이터: 선택 기간 CSV 내보내기, 휴지통 조회·복원·영구 삭제
- 계정: 로그아웃

개인 장부는 삭제할 수 없다. 공동 장부 삭제는 소유자만 가능하며 장부 이름 재입력 확인 후 거래, 분류, 구성원, 초대를 함께 영구 삭제한다. 참여자가 남아 있어도 삭제할 수 있지만 복구할 수 없음을 명확히 경고한다.

CSV는 UTF-8 BOM을 포함해 한국어 스프레드시트에서 바로 열 수 있게 한다. 거래일, 유형, 분류, 내용, 금액, 메모, 입력자, 입력 시각 열을 내보내며 휴지통 거래는 제외한다.

## 9. 기간과 통계 계산

### 9.1 정산 기간

정산 기간의 라벨은 시작일이 속한 달을 사용한다.

- 시작일 1: 2026년 8월 기간은 2026-08-01 이상 2026-09-01 미만
- 시작일 10: 2026년 8월 기간은 2026-08-10 이상 2026-09-10 미만
- 말일: 2026년 1월 기간은 2026-01-31 이상 2026-02-28 미만

구현은 종료일 포함 계산 대신 `[시작 시각, 다음 기간 시작 시각)`의 반개구간을 사용한다. 화면에는 사용자가 이해하기 쉽도록 종료일을 다음 기간 시작일의 전날로 표시한다. 말일은 각 달의 실제 마지막 날짜를 사용하므로 윤년 2월도 자연스럽게 처리된다.

가계부 탭에서 직접 기간을 선택하면 선택 시작일 이상, 선택 종료일 다음 날 미만을 사용한다.

### 9.2 금액 집계

- 총수입: 삭제되지 않은 `income` 거래 금액 합계
- 총지출: 삭제되지 않은 `expense` 거래 금액 합계
- 차액: 총수입 - 총지출
- 분류 비율: 해당 분류 금액 / 선택 유형 전체 금액
- 선택 유형 전체 금액이 0이면 모든 분류 비율은 0
- 절세 납입 합계: 해당 목표의 납입 내역 합계
- 절세 남은 금액: `max(목표 금액 - 납입 합계, 0)`
- 절세 초과 금액: `max(납입 합계 - 목표 금액, 0)`

통계 집계는 로그인 사용자 세션으로 호출하는 `security invoker` Postgres RPC 함수로 구현한다. 기간별 요약 함수와 분류별 상세 함수는 장부 ID와 기간을 입력받고 RLS로 허용된 삭제되지 않은 거래만 집계한다. 서비스 역할 키로 통계를 계산하지 않는다.

## 10. 사용자 흐름

### 10.1 첫 가입

1. 사용자가 가입 정보를 입력한다.
2. 서버와 DB가 형식과 고유성을 검증한다.
3. 계정, 프로필, 개인 장부, 기본 분류를 생성한다.
4. 이메일 확인을 요구하지 않고 로그인 세션을 만든다.
5. 빈 개인 장부의 가계부 탭으로 이동한다.
6. `첫 거래 추가` 행동을 안내한다.

### 10.2 공동 장부

1. 사용자가 공동 장부를 생성하면 생성자가 소유자가 된다.
2. 소유자가 기존 사용자의 아이디 또는 이메일을 입력한다.
3. 대상 사용자의 앱에 대기 초대가 표시된다.
4. 대상이 수락하면 구성원 행을 만들고 장부 선택기에 추가한다.
5. 거절하거나 7일이 지나면 초대를 사용할 수 없다.

### 10.3 거래 저장

1. 폼은 필수값과 유형·분류 일치를 클라이언트에서 먼저 검증한다.
2. 저장 버튼을 잠그고 요청별 멱등성 키와 함께 등록한다.
3. DB 제약과 RLS가 입력을 다시 검증한다.
4. 성공하면 목록, 합계, 관련 통계 캐시를 갱신한다.
5. 실패하면 폼 내용을 유지하고 구체적인 수정 가능 오류 또는 재시도 안내를 보여준다.

### 10.4 거래 삭제

1. 사용자가 삭제를 확인한다.
2. 권한이 있으면 거래를 휴지통으로 이동한다.
3. 일반 목록과 통계에서 즉시 제외한다.
4. 소유자는 휴지통에서 복원하거나 영구 삭제한다.

## 11. 유효성 검사와 오류 처리

- 금액은 1원 이상, `bigint` 범위 안의 정수여야 한다.
- 거래 내용, 거래일, 유형, 분류는 필수다.
- 납입일과 거래일은 유효한 달력 날짜여야 한다.
- 검색어와 메모 길이에 상한을 두어 비정상적으로 큰 요청을 막는다.
- 저장 중 같은 폼의 재제출을 막고 DB 멱등성 키로 재시도 중복도 막는다.
- 네트워크 실패 시 입력값을 유지한다.
- 인증 오류는 계정 존재 여부와 무관하게 동일한 메시지를 사용한다.
- 세션 만료 시 현재 URL을 보존한 로그인 화면으로 보내고 로그인 후 복귀한다.
- 접근 권한을 잃은 장부는 안내 후 개인 장부로 이동한다.
- 로딩 중에는 화면 구조를 유지하는 스켈레톤을 보여준다.
- 데이터가 없으면 원인과 다음 행동을 함께 안내한다.
- 서버 오류에는 사용자용 추적 ID를 표시하되 민감한 내부 정보는 숨긴다.

## 12. PWA와 동기화

서비스 워커는 앱 셸과 정적 자산만 캐시한다. 인증 데이터, 거래, 통계 응답은 오프라인 영구 캐시에 저장하지 않는다. 첫 버전에서 거래 등록·수정·삭제는 인터넷 연결이 필요하다.

본인 저장 결과는 즉시 화면에 반영한다. 다른 사용자의 변경은 다음 시점에 다시 조회한다.

- 장부 또는 탭 전환
- 브라우저 탭이 다시 활성화될 때
- 사용자가 새로고침을 실행할 때

동일 거래를 두 사용자가 동시에 수정하는 경우 첫 버전은 마지막으로 성공한 저장 결과를 사용한다. 참여자는 타인의 거래를 수정할 수 없으므로 실제 충돌 범위는 소유자와 원 작성자의 동시 수정으로 제한된다. 화면은 갱신 시 최신 서버 값을 표시한다.

## 13. 보안과 개인정보

- 모든 노출 테이블에서 RLS를 활성화한다.
- 마이그레이션에서 `anon`과 `authenticated` grants를 명시적으로 제한한다.
- 공개 프로필과 비공개 연락처를 분리하여 열 단위 노출 위험을 없앤다.
- 서비스 역할 키는 서버 전용 모듈 외부에서 가져올 수 없게 한다.
- 브라우저 요청의 사용자 ID를 신뢰하지 않고 세션의 `auth.uid()`를 사용한다.
- 입력값은 클라이언트, 서버, 데이터베이스의 세 단계에서 검증한다.
- 인증 토큰, 비밀번호, 전화번호, 전체 이메일을 애플리케이션 로그에 기록하지 않는다.
- CSV 내보내기는 서버에서 장부 소유자 권한과 기간을 다시 검증한다.
- 오류 응답으로 아이디 또는 이메일 등록 여부를 추론할 수 없게 한다.
- 휴지통 영구 삭제는 재확인을 요구하고 복구 불가임을 명시한다.
- 절세 화면에 자동 세무 판단이 아님을 명확히 표시한다.

## 14. 테스트 전략

### 14.1 단위 테스트

- 시작일 1~28과 말일 정산 기간 계산
- 28·29·30·31일, 윤년 2월, 연도 경계
- 직접 선택 기간의 양 끝 날짜 포함 여부
- 수입, 지출, 차액, 분류 비율
- 0원 통계와 절세 목표 초과 납입
- 입력 정규화와 유효성 검사

### 14.2 데이터베이스 및 RLS 테스트

Supabase CLI와 pgTAP으로 각 정책을 같은 마이그레이션 단위에서 검증한다.

- 비로그인 사용자 접근 거부
- 사용자 A가 사용자 B의 개인 장부를 조회할 수 없음
- 공동 장부 구성원은 삭제되지 않은 전체 거래를 조회할 수 있음
- 일반 참여자는 본인 거래만 수정·휴지통 이동 가능
- 소유자는 모든 거래 관리 가능
- 일반 참여자는 분류와 기준일을 변경할 수 없음
- 탈퇴한 구성원은 즉시 접근할 수 없음
- 절세 데이터는 본인만 접근 가능
- 휴지통과 CSV는 소유자만 접근 가능

### 14.3 통합 테스트

- 가입 후 프로필, 개인 장부, 구성원, 기본 분류가 모두 생성됨
- 아이디 로그인과 이메일 로그인이 같은 계정 세션을 생성함
- 비밀번호 재설정 콜백
- 공동 장부 초대 수락·거절·만료
- 거래 저장 후 요약과 통계가 일치함
- 분류 비활성화 후 기존 거래가 정상 표시됨
- 거래 복원 후 통계에 다시 포함됨

### 14.4 E2E 테스트

Playwright로 모바일과 PC 뷰포트를 각각 검증한다.

- 가입 → 첫 거래 → 요약 확인
- 공동 장부 생성 → 두 번째 사용자 초대 → 양쪽 거래 입력
- 권한에 따른 편집 버튼 노출과 서버 차단
- 통계 기간 선택 → 분류 상세 → 원본 거래 확인
- 절세 목표 → 납입 추가 → 진행률 갱신
- 거래 삭제 → 휴지통 → 복원 → CSV 내보내기
- PWA 매니페스트와 설치 가능 조건

## 15. 운영과 관찰성

- Vercel Preview 배포마다 빌드, 타입 검사, 단위 테스트를 실행한다.
- 운영 마이그레이션 전에 개발 Supabase에서 RLS 테스트를 통과시킨다.
- 서버 오류는 민감정보를 제외한 추적 ID, 경로, 오류 종류만 기록한다.
- 클라이언트에는 사용자가 조치할 수 있는 메시지와 추적 ID만 보여준다.
- 데이터베이스 마이그레이션은 롤백 또는 보정 마이그레이션 전략을 함께 검토한다.
- 운영 비밀값은 Vercel 환경변수와 Supabase 설정에서만 관리하며 저장소에 커밋하지 않는다.
