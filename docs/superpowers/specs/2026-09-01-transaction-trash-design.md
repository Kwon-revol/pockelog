# PockeLog 거래 휴지통 설계

## 1. 목표와 범위

현재 선택한 개인 또는 공동 장부에서 휴지통으로 이동한 거래를 장부 소유자가 조회하고, 복원하거나 영구 삭제할 수 있게 한다. 삭제 거래는 자동으로 만료하지 않으며 소유자가 직접 처리할 때까지 보관한다.

이번 범위에는 CSV 내보내기, 일괄 복원·삭제, 자동 보관 기간, 일반 구성원의 휴지통 접근, 삭제 취소 토스트를 포함하지 않는다.

## 2. 사용자와 권한

- 개인 장부와 공동 장부 모두 장부 소유자만 휴지통을 조회할 수 있다.
- 공동 장부의 일반 구성원은 설정 카드가 보이지 않으며 `/settings/trash`를 직접 열어도 데이터를 조회할 수 없다.
- 모든 조회·복원·영구 삭제 함수는 브라우저가 보낸 사용자 ID를 받지 않고 `auth.uid()`와 실제 장부 소유권을 검사한다.
- 권한을 잃거나 현재 장부가 존재하지 않으면 휴지통 데이터를 노출하지 않고 설정 화면으로 돌아갈 수 있는 안내를 표시한다.

## 3. 화면 구조

설정 화면에 소유자 전용 `데이터 관리` 카드를 추가한다. 카드의 `휴지통 보기` 링크는 `/settings/trash`로 이동한다.

휴지통 화면은 현재 장부 이름과 휴지통 설명을 상단에 표시한다. 모바일은 카드 목록, PC는 표를 사용하며 각 항목에 다음 정보를 보여준다.

- 사용 날짜
- 내용과 메모
- 분류와 수입·지출 유형
- 금액
- 작성자
- 삭제 시각

삭제 시각 내림차순, 거래 ID 내림차순으로 정렬한다. 첫 50건을 표시하고 감지 지점이 보이면 커서 기반으로 다음 50건을 자동 조회한다. 마지막 페이지에는 완료 문구를 표시하지 않는다.

휴지통이 비어 있으면 `휴지통이 비어 있어요`와 가계부로 돌아가는 링크를 표시한다.

## 4. 사용자 동작

### 4.1 복원

사용자가 복원 버튼을 누르면 확인 대화상자를 표시한다. 승인 후 서버가 소유권과 거래 상태를 다시 검사하고 `deleted_at`, `deleted_by`를 `null`로 되돌린다.

성공한 항목은 휴지통 목록에서 즉시 제거한다. 가계부, 통계, 세금 화면 캐시를 무효화하므로 해당 거래가 각 집계에 다시 포함된다. 기존 분류가 비활성화되어 있어도 원래 분류와 유형을 바꾸지 않는 복원은 허용한다.

### 4.2 영구 삭제

사용자가 영구 삭제 버튼을 누르면 `이 내역은 복구할 수 없습니다`라는 명시적 경고와 확인 대화상자를 표시한다. 승인 후 서버가 소유권과 삭제 상태를 다시 검사하고 거래 행을 실제로 삭제한다.

성공한 항목은 목록에서 즉시 제거한다. 이미 복원됐거나 존재하지 않는 거래에는 다른 사용자의 데이터 존재 여부를 드러내지 않는 공통 실패 메시지를 반환한다.

### 4.3 요청 상태와 오류

- 처리 중인 항목의 복원·영구 삭제 버튼을 모두 잠가 중복 요청을 막는다.
- 실패하면 항목을 목록에 유지하고 해당 항목에 재시도 가능한 오류를 표시한다.
- 세션 만료 시 `/login?next=/settings/trash`로 이동한다.
- 추가 페이지 조회 실패 시 기존 항목을 유지하고 다시 시도 버튼을 표시한다.

## 5. 데이터베이스 설계

새 보정 마이그레이션 `202609010007_transaction_trash.sql`을 추가한다. 기존 RLS는 일반 조회에서 `deleted_at is null`인 행만 허용하므로 휴지통 기능은 소유권을 내부에서 검사하는 제한된 `security definer` 함수로 구현한다.

### 5.1 조회 함수

`get_deleted_transactions(target_ledger_id, cursor_deleted_at, cursor_id, page_size)`는 다음을 수행한다.

- `auth.uid()`가 대상 장부 소유자인지 검사한다.
- 삭제된 거래만 반환한다.
- 분류명·색상, 작성자 이름, 삭제 시각을 함께 반환한다.
- `(deleted_at, id)` 커서와 최대 50건 제한을 적용한다.
- 접근 불가 장부는 데이터가 없는 것처럼 반환하지 않고 권한 오류를 발생시켜 애플리케이션이 명확히 처리하게 한다.

### 5.2 변경 함수

- `restore_deleted_transaction(target_transaction_id)`는 소유한 장부의 삭제 거래만 복원한다.
- `permanently_delete_transaction(target_transaction_id)`는 소유한 장부의 삭제 거래만 영구 삭제한다.
- 두 함수는 대상 행을 `for update`로 잠가 동시 복원·삭제를 직렬화한다.
- 결과는 `restored`, `deleted`, `missing` 중 하나로 반환하고 권한 오류는 PostgreSQL `42501`을 사용한다.

### 5.3 권한과 안전성

- 함수의 `search_path`는 빈 값으로 고정하고 모든 객체를 완전 수식한다.
- `PUBLIC`, `anon` 실행 권한을 명시적으로 제거하고 `authenticated`에만 실행 권한을 부여한다.
- 일반 사용자의 `transactions` 테이블 직접 `delete` 권한은 계속 부여하지 않는다.
- 마이그레이션은 함수와 권한을 `create or replace`, `revoke`, `grant`로 선언해 재실행해도 같은 상태가 되게 한다.

## 6. 애플리케이션 구조

휴지통 기능은 `src/features/trash/` 아래에 타입, 스키마, 도메인 워크플로, Supabase 게이트웨이, 조회, 서버 액션, 화면을 분리한다.

- 서버 페이지: 인증과 초기 데이터 조회, 권한 오류 처리
- API 경로: 다음 커서 페이지 조회
- 서버 액션: 복원·영구 삭제 입력 검증, 결과 매핑, 관련 경로 재검증
- 클라이언트 화면: 반응형 목록, 무한 스크롤, 항목별 처리 상태와 오류

설정 화면은 휴지통 구현 세부사항을 알지 않고 소유자일 때 전용 링크만 렌더링한다.

## 7. 캐시와 동기화

복원 또는 영구 삭제 성공 시 `/settings/trash`, `/ledger`, `/statistics`, `/tax-goals`를 재검증한다. 현재 화면에서는 성공 결과를 즉시 제거하고, 서버가 새 초기 데이터를 전달하면 서버 데이터 키로 로컬 페이지 상태를 교체한다.

다른 브라우저나 공동 사용자의 변경은 새로고침, 탭 재활성화 또는 장부 전환 때 최신 서버 상태를 읽는다.

## 8. 테스트 전략

### 8.1 데이터베이스 계약

- 소유자는 본인 장부의 삭제 거래만 조회한다.
- 공동 장부 일반 구성원과 비구성원은 조회·복원·영구 삭제할 수 없다.
- 복원 후 일반 거래 조회와 통계 합계에 다시 포함된다.
- 비활성 분류를 가진 거래도 복원된다.
- 영구 삭제 후 거래가 실제로 사라진다.
- 활성 거래는 휴지통 함수로 복원·영구 삭제할 수 없다.
- 동시 또는 반복 요청은 한 번만 상태를 변경한다.

### 8.2 단위·UI 테스트

- 커서 인코딩·검증과 50건 페이지 경계를 검사한다.
- 세션 없음, 소유권 없음, 누락, DB 실패를 안전한 결과로 매핑한다.
- 모바일 카드와 PC 표에 동일한 정보를 표시한다.
- 성공 시 항목 제거, 실패 시 항목 유지, 중복 클릭 차단을 검사한다.
- 무한 스크롤의 중복 요청 방지와 마지막 페이지 완료 문구 미표시를 검사한다.
- 설정 화면에서 소유자에게만 휴지통 링크가 보이는지 검사한다.

### 8.3 통합 검증

전체 단위 테스트, TypeScript, ESLint, Next.js 프로덕션 빌드를 실행한다. 호스팅된 개발 Supabase 안전 설정이 있는 경우에만 모바일·PC E2E로 삭제 → 휴지통 → 복원 → 재삭제 → 영구 삭제 흐름을 검증한다.

## 9. 배포 순서

1. Supabase SQL Editor에서 `202609010007_transaction_trash.sql`을 한 번 실행한다.
2. 제공된 안전 확인 SQL로 함수·권한·RLS 상태를 확인한다.
3. 애플리케이션 코드를 `main`에 배포한다.
4. Vercel 배포가 준비된 후 소유자와 일반 구성원 계정으로 접근 권한을 확인한다.

앱 코드가 먼저 배포되어 함수가 아직 없으면 설정의 휴지통 링크는 표시하되, 휴지통 화면에서 준비되지 않았다는 안전한 오류 안내를 제공하고 기존 설정 기능에는 영향을 주지 않는다.
