# PockeLog 통계 그룹 설계

- 문서 상태: 사용자 승인 완료 설계안
- 작성일: 2026-09-11
- 기준 브랜치: `main`
- 대상 기능: 장부별 수입·지출 통계 그룹 관리와 계층형 통계 표시

## 1. 목적과 성공 기준

PockeLog 사용자가 거래 입력용 상세 분류를 변경하지 않고도 통계 화면에서 관련 분류를 상위 그룹으로 묶어 볼 수 있게 한다. 예를 들어 `주거비`, `통신비`는 `고정지출`로, `IRP`, `연금저축`, `적금`은 `저축`으로 묶는다.

다음 조건을 모두 만족하면 완료로 본다.

- 통계 그룹은 장부별로 저장되고 공동 장부 구성원 모두에게 동일하게 보인다.
- 수입 그룹과 지출 그룹은 분리된다.
- 한 상세 분류는 같은 시점에 하나의 통계 그룹에만 속할 수 있다.
- 그룹에 속한 분류는 통계에서 그룹 합계로 묶이며 그룹을 펼치면 하위 분류별 금액과 비율을 볼 수 있다.
- 그룹에 속하지 않은 분류는 기존과 동일하게 분류명으로 표시된다.
- 통계 그룹이 하나도 없는 장부의 통계 화면은 현재 화면과 같은 정보를 표시한다.
- 그룹 설정은 개인 장부 소유자 또는 공동 장부 소유자만 변경할 수 있다.
- 가계부 거래 입력과 원본 거래 목록에는 통계 그룹이 노출되지 않는다.

## 2. 범위

### 2.1 포함

- 장부별 수입·지출 통계 그룹 생성, 수정, 삭제, 순서 변경
- 그룹 이름과 색상 설정
- 상세 분류의 그룹 배치 및 다른 그룹으로 이동
- 설정 화면의 소유자 전용 그룹 관리 UI
- 일반 구성원의 읽기 전용 그룹 구성 표시
- 통계 상세 화면의 그룹 합계와 펼칠 수 있는 하위 분류
- 그룹 미지정 분류의 기존 단독 표시
- 데이터베이스 RLS, 무결성 검사, 원자적 변경 함수
- 단위, 컴포넌트, 데이터베이스 계약, 안전한 E2E 테스트
- Supabase 적용 및 배포 문서

### 2.2 제외

- 가계부 입력 화면에서 통계 그룹 선택
- 거래가 통계 그룹을 직접 참조하는 구조
- 한 분류의 다중 그룹 소속
- 사용자 개인별로 서로 다른 공동 장부 그룹 구성
- 그룹별 예산, 알림, 반복 거래
- 그룹 간 계층 또는 2단계를 초과하는 통계 구조
- 통계 그룹을 세금 계산 규칙으로 사용하는 기능

## 3. 데이터 모델

### 3.1 `public.statistics_groups`

장부에 속하는 통계 그룹을 저장한다.

| 열 | 형식 | 규칙 |
| --- | --- | --- |
| `id` | `uuid` | 기본키, `gen_random_uuid()` |
| `ledger_id` | `uuid` | `public.ledgers(id)` 참조, 장부 삭제 시 cascade |
| `type` | `public.transaction_type` | `income` 또는 `expense` |
| `name` | `text` | 공백 제거 후 1~30자 |
| `color` | `text` | `#RRGGBB` 형식 |
| `sort_order` | `integer` | 같은 장부·유형 안의 표시 순서, 0 이상 |
| `created_at` | `timestamptz` | 생성 시각 |
| `updated_at` | `timestamptz` | 수정 시각 |

같은 `ledger_id`, `type` 안에서 공백을 제거하고 대소문자를 무시한 그룹 이름은 유일해야 한다. 목록 조회를 위해 `(ledger_id, type, sort_order, id)` 인덱스를 둔다.

### 3.2 `public.categories.statistics_group_id`

기존 상세 분류에 nullable `uuid` 열을 추가하고 `public.statistics_groups(id) on delete set null`을 참조한다. 하나의 열만 사용하므로 상세 분류 하나가 여러 그룹에 중복 소속될 수 없다.

데이터베이스 트리거는 연결하려는 그룹과 분류의 `ledger_id`와 `type`이 모두 같은지 검사한다. 조건이 다르면 변경을 거부한다. 그룹 삭제 시 외래키가 상세 분류를 삭제하지 않고 연결만 해제한다.

거래는 계속 `category_id`만 참조한다. 통계 그룹 변경은 과거 거래를 수정하거나 복제하지 않으며, 조회 시점의 상세 분류 연결을 기준으로 과거 기간 통계에도 반영된다.

## 4. 권한과 보안

- 장부 구성원은 현재 장부의 통계 그룹과 상세 분류의 그룹 연결을 조회할 수 있다.
- 개인·공동 장부 소유자만 통계 그룹을 생성, 수정, 삭제, 정렬할 수 있다.
- 소유자만 해당 장부 상세 분류의 `statistics_group_id`를 변경할 수 있다.
- 일반 구성원은 설정 화면에서 그룹 구성을 확인하고 통계 결과를 볼 수 있지만 변경할 수 없다.
- 다른 장부의 그룹·분류 연결, 수입 그룹과 지출 분류의 연결, 지출 그룹과 수입 분류의 연결은 거부한다.
- 변경 함수는 사용자 ID를 입력으로 신뢰하지 않고 `auth.uid()`와 장부 멤버십을 기준으로 권한을 판단한다.
- 함수는 고정된 `search_path`와 최소 실행 권한을 사용한다.

## 5. 데이터베이스 변경 API

`202609110009_statistics_groups.sql` 마이그레이션에서 다음 기능을 추가한다.

- 통계 그룹 테이블, 인덱스, 갱신 시각 트리거, RLS 및 grants
- 상세 분류의 그룹 연결 열과 동일 장부·유형 무결성 트리거
- 그룹 생성·수정·삭제 함수
- 같은 유형의 전체 그룹 ID 목록을 받아 표시 순서를 원자적으로 저장하는 함수
- 그룹 ID와 상세 분류 ID 목록을 받아 소속을 원자적으로 교체하는 함수
- 그룹 메타데이터를 포함한 새로운 분류 통계 조회 함수

그룹 소속 교체 함수는 대상 그룹과 같은 장부·유형의 분류만 허용한다. 전달된 분류는 기존 그룹에서 자동으로 빠지고 대상 그룹에 연결된다. 대상 그룹에서 제외된 기존 분류는 그룹 미지정 상태가 된다. 전체 검증이 끝나기 전에는 어떤 연결도 변경하지 않는다.

현재 배포가 마이그레이션 선적용 중에도 계속 동작하도록 기존 `get_category_statistics` 함수는 유지한다. 새 애플리케이션은 그룹 정보를 반환하는 새 함수만 사용한다.

## 6. 설정 화면

설정 탭의 수입·지출 분류 관리 다음에 `통계 그룹 관리` 영역을 추가한다.

### 6.1 공통 표시

- `지출 그룹`, `수입 그룹` 탭을 제공한다.
- 각 그룹 카드에는 색상, 이름, 포함된 상세 분류, 표시 순서를 보여 준다.
- 그룹에 포함되지 않은 상세 분류도 별도 목록으로 알려 설정 상태를 파악할 수 있게 한다.
- 숨긴 상세 분류도 그룹 소속을 유지하고 그룹 편집 목록에 표시한다. 숨김 여부를 함께 표시해 혼동을 줄인다.

### 6.2 소유자 동작

- 그룹 추가 버튼으로 이름, 색상, 포함할 상세 분류를 설정한다.
- 그룹 수정에서 이름, 색상, 상세 분류 선택을 함께 변경한다.
- 다른 그룹에 속한 상세 분류를 선택하면 저장 시 새 그룹으로 이동한다는 안내를 표시한다.
- 위·아래 이동 버튼으로 같은 유형 안의 그룹 순서를 변경한다.
- 삭제 전 확인을 받고, 삭제하면 상세 분류와 거래는 유지한 채 연결만 해제한다.
- 저장 중에는 관련 변경 버튼을 잠그고 성공 후 서버 데이터를 다시 조회한다.

### 6.3 일반 구성원

일반 구성원에게는 그룹 구성과 포함 분류를 읽기 전용으로 표시한다. 생성, 수정, 삭제, 정렬 버튼은 렌더링하지 않는다. 서버와 데이터베이스도 같은 권한을 다시 검증한다.

## 7. 통계 상세 화면

현재 수입·지출 전환과 원본 거래 목록은 유지한다. 분류별 비율 영역만 계층형 항목을 지원하도록 확장한다.

### 7.1 그룹 항목

- 그룹 합계는 포함된 상세 분류 금액의 합이다.
- 그룹 비율은 `그룹 합계 / 현재 수입 또는 지출 합계 * 100`이다.
- 행에는 그룹 색상, 이름, 합계, 비율, 진행 막대, 펼치기 상태를 표시한다.
- 그룹 행을 누르면 하위 상세 분류 목록을 펼치거나 접는다.
- 하위 분류는 기존 분류 색상, 분류명, 금액, 현재 유형 전체 대비 비율을 표시한다.
- 선택 기간에 금액이 없는 빈 그룹은 표시하지 않는다.

### 7.2 그룹 미지정 항목

그룹에 속하지 않은 상세 분류는 기존과 같은 단독 항목으로 표시한다. 별도의 `미분류` 합계로 합치지 않는다.

통계 그룹이 하나도 없거나 해당 기간에 그룹에 속한 거래가 없으면 모든 항목이 기존 분류별 통계처럼 보인다.

### 7.3 순서

최상위 목록에는 그룹 항목을 먼저 설정한 그룹 순서대로 표시하고, 그 뒤에 그룹 미지정 상세 분류를 기존 상세 분류 순서대로 표시한다. 순서가 같은 항목은 금액 내림차순과 안정적인 ID 순서로 정렬해 결과가 새로고침마다 바뀌지 않게 한다.

## 8. 서버 조회와 집계

새 통계 RPC는 기존 분류 통계 행에 다음 그룹 정보를 추가해 반환한다.

- `statistics_group_id`
- `statistics_group_name`
- `statistics_group_color`
- `statistics_group_sort_order`

RPC는 거래와 상세 분류를 기준으로 분류별 합계를 계산하므로 통계 그룹 변경 시 거래 데이터를 다시 계산하거나 이전할 필요가 없다. 서버 워크플로는 반환된 분류 행을 다음 규칙으로 계층화한다.

1. 그룹 ID가 있는 행은 같은 그룹끼리 묶고 금액을 합산한다.
2. 그룹 ID가 없는 행은 단독 분류 항목으로 유지한다.
3. 그룹과 하위 분류 비율은 현재 유형 전체 합계를 분모로 계산한다.
4. 빈 그룹은 RPC 결과에 없으므로 통계 화면에도 나타나지 않는다.
5. 통계 원본 거래 페이지의 필터와 무한 스크롤은 변경하지 않는다.

금액 합계는 데이터베이스의 정수 합계를 사용하고, 비율은 기존과 동일하게 화면에서 최대 한 자리 소수로 표시한다. 반올림된 항목 비율의 합이 정확히 100.0이 아닐 수 있지만 금액 합계는 반드시 현재 유형 합계와 일치해야 한다.

## 9. 오류 처리

- 그룹 이름·색상·분류 목록 입력은 서버 액션 호출 전에 스키마로 검증한다.
- 중복 이름은 `같은 이름의 통계 그룹이 있어요.`로 안내한다.
- 다른 장부, 유형 불일치 또는 일반 구성원의 변경은 권한 오류로 통일한다.
- 저장 실패 시 열린 편집 화면과 사용자가 입력한 값은 유지한다.
- 통계 그룹 스키마가 아직 적용되지 않은 배포에서는 설정 화면에 마이그레이션 필요 안내를 표시하고, 통계 화면은 기존 `get_category_statistics` RPC로 다시 조회해 기존 분류별 통계를 제공한다.
- 통계 그룹 조회 자체가 실패하면 기존 오류 화면 규칙을 사용하며 잘못된 부분 합계를 표시하지 않는다.

## 10. 테스트 전략

### 10.1 도메인 및 워크플로 테스트

- 그룹 이름, 색상, 유형, 상세 분류 ID 목록 검증
- 생성, 수정, 삭제, 정렬, 소속 교체 결과와 오류 매핑
- 분류 행의 그룹화, 그룹 합계, 비율, 순서
- 그룹이 없음, 빈 그룹, 미지정 분류, 숨긴 분류, 0원 기간
- 한 분류를 다른 그룹으로 옮길 때 중복 합계가 생기지 않음

### 10.2 데이터베이스 계약 테스트

- 소유자 CRUD와 일반 구성원 변경 거부
- 구성원 조회와 비구성원 조회 거부
- 다른 장부 분류 연결 거부
- 수입·지출 유형 불일치 거부
- 그룹 삭제 시 상세 분류 연결만 해제
- 소속 교체 함수의 원자성과 그룹 이름 유일성
- 새 통계 RPC의 그룹 메타데이터와 기존 금액 합계

### 10.3 UI 및 E2E 테스트

- 설정 화면의 유형 탭, 그룹 폼, 색상, 분류 선택, 이동 안내
- 소유자 제어 버튼과 일반 구성원의 읽기 전용 화면
- 통계 그룹 합계 및 하위 분류 펼치기·접기
- 그룹 미지정 분류와 그룹이 없는 기존 화면
- PC와 모바일 레이아웃
- 전용 개발 Supabase 안전 장치가 켜진 경우에만 실제 그룹 변경 E2E 실행

### 10.4 전체 품질 게이트

- 단위·컴포넌트 테스트
- TypeScript 검사
- ESLint
- 프로덕션 빌드
- 공개 E2E
- 가능한 환경에서는 pgTAP 데이터베이스 계약과 호스팅 통합 E2E

## 11. 배포와 롤백

배포 순서는 다음과 같다.

1. Supabase SQL Editor에서 `202609110009_statistics_groups.sql`을 실행한다.
2. 검증 쿼리로 테이블, 열, RLS, 함수와 권한을 확인한다.
3. 애플리케이션 코드를 GitHub와 Vercel에 배포한다.
4. 소유자와 일반 구성원 계정으로 설정·통계를 점검한다.

마이그레이션을 먼저 적용해도 기존 애플리케이션은 기존 통계 RPC를 사용하므로 계속 동작한다. 애플리케이션 롤백 시 새 테이블과 nullable 연결 열은 남겨 두어도 기존 기능에 영향을 주지 않는다. 운영 데이터가 들어간 뒤에는 마이그레이션을 역으로 삭제하지 않고 애플리케이션만 이전 버전으로 되돌리는 방식을 기본 롤백으로 사용한다.

## 12. 향후 확장

이번 구조는 그룹별 예산, 기간 비교, 결제수단 통계 같은 후속 기능의 기반으로 사용할 수 있다. 다만 이번 구현에는 해당 기능을 포함하지 않으며, 거래 입력 분류와 통계 그룹의 역할을 계속 분리한다.
