# PockeLog 공동 장부 설계

## 1. 목표

로그인 사용자가 개인 장부와 별도로 공동 장부를 만들고, 이미 가입한 사용자를 아이디 또는 이메일로 초대해 함께 거래를 기록할 수 있게 한다. 장부 소유자와 일반 참여자의 권한을 데이터베이스 RLS와 원자적 함수로 강제하며, 모바일과 PC에서 동일한 장부 전환·초대·구성원 관리 흐름을 제공한다.

## 2. 이번 범위

- 공동 장부 생성과 기본 수입·지출 분류 생성
- 현재 사용자가 참여 중인 장부 목록 조회와 기본 장부 전환
- 아이디 또는 이메일로 기존 사용자 검색 후 7일짜리 앱 내부 초대 생성
- 대기 초대 수락·거절, 소유자의 초대 취소
- 소유자의 구성원 제거, 참여자의 공동 장부 나가기
- 이름 재입력 확인을 거친 공동 장부 영구 삭제
- 공동 장부 거래 목록의 입력자 표시
- 기존 거래 수정·휴지통 권한을 소유자 또는 작성자로 제한
- 모바일·PC 화면, 단위 테스트, RLS/pgTAP 계약, 호스팅 개발 환경 E2E

## 3. 제외 범위

- 미가입자에게 보내는 초대 이메일
- 공동 장부 소유권 이전
- 개인 장부 삭제
- 초대 링크 공유나 공개 참여 코드
- 여러 단계의 역할 체계와 구성원별 세부 권한
- 실시간 동기화 알림

## 4. 핵심 설계 결정

### 4.1 원자적 데이터 변경

공동 장부 생성, 초대 응답, 구성원 제거, 나가기, 삭제는 여러 테이블의 상태가 함께 바뀐다. 이 작업들은 Postgres 함수에서 하나의 트랜잭션으로 처리한다. 함수는 호출자와 대상 장부를 직접 검증하며, 브라우저가 `service_role` 키를 사용하지 않게 한다.

일반 조회와 거래·통계 요청은 계속 로그인 사용자의 Supabase 세션과 RLS를 사용한다. `service_role`은 초대 입력값을 비공개 로그인 식별자에서 사용자 ID로 바꾸는 서버 전용 조회 한 곳에만 사용한다.

### 4.2 기존 사용자에게만 초대

소유자가 아이디 또는 이메일을 입력하면 서버 전용 `resolve_invitation_target` 함수가 `private.account_identifiers`를 조회한다. 이 함수는 `service_role`에만 실행 권한을 부여하고 이메일이나 다른 계정 정보를 반환하지 않으며 대상 UUID만 반환한다. 대상이 없다는 결과도 동일한 일반 오류로 표시해 계정 존재 여부 노출을 줄인다.

대상 UUID를 얻은 뒤 초대 생성 자체는 소유자의 로그인 세션으로 실행한다. 서버는 본인 초대, 개인 장부 초대, 이미 구성원인 사용자, 동일 대상의 대기 초대를 거부한다.

## 5. 데이터 모델

### 5.1 `public.ledger_invitations`

- `id uuid primary key`
- `ledger_id uuid not null references public.ledgers on delete cascade`
- `target_user_id uuid not null references auth.users on delete cascade`
- `invited_by uuid not null references auth.users`
- `status ledger_invitation_status not null default 'pending'`
- `expires_at timestamptz not null default now() + interval '7 days'`
- `created_at timestamptz not null default now()`
- `responded_at timestamptz`

`ledger_invitation_status`는 `pending`, `accepted`, `declined`, `revoked`, `expired`를 가진다. `(ledger_id, target_user_id)`에 대해 `pending` 상태만 고유한 부분 인덱스를 둔다. `expires_at`은 생성 시점보다 뒤여야 하고, 응답이 끝난 초대는 `responded_at`을 기록한다.

목록 조회는 `pending`이지만 기한이 지난 행을 `expired`로 계산해 보여준다. 모든 응답·취소 함수도 먼저 만료 여부를 검사하고 만료 상태를 기록하므로 7일이 지난 초대는 절대 수락할 수 없다. 별도 유료 스케줄러는 사용하지 않는다.

### 5.2 기존 테이블 활용

- `public.ledgers.kind = 'shared'`인 행이 공동 장부다.
- 생성자는 `owner_id`와 `ledger_members.role = 'owner'`로 기록한다.
- 초대 수락 시 `ledger_members.role = 'member'` 행을 추가한다.
- `user_private_profiles.default_ledger_id`가 모든 화면에서 현재 선택 장부를 결정한다.
- 탈퇴·제거·삭제 때문에 현재 장부 접근권한이 사라지면 해당 사용자의 개인 장부로 기본 장부를 되돌린다.

구성원 삭제 트리거는 삭제된 사용자의 기본 장부가 해당 장부일 때 그 사용자가 소유한 개인 장부로 변경한다. 이 트리거는 제한된 `security definer` 함수로 작성해 다른 사용자의 비공개 프로필을 임의로 변경할 수 없게 한다.

## 6. 데이터베이스 함수와 권한

### 6.1 함수

- `create_shared_ledger(name) -> uuid`: 이름 검증, 공동 장부·소유자 구성원·기본 분류 생성, 새 장부를 현재 장부로 선택
- `resolve_invitation_target(identifier) -> uuid`: 서비스 역할 전용 아이디/이메일 조회
- `create_ledger_invitation(ledger_id, target_user_id) -> uuid`: 소유자와 대상 상태 검증 후 초대 생성
- `respond_to_ledger_invitation(invitation_id, response)`: 대상 본인만 수락 또는 거절, 수락 시 구성원 추가
- `revoke_ledger_invitation(invitation_id)`: 해당 장부 소유자만 대기 초대 취소
- `remove_ledger_member(ledger_id, user_id)`: 소유자만 일반 참여자 제거
- `leave_shared_ledger(ledger_id)`: 일반 참여자 본인만 나가기
- `delete_shared_ledger(ledger_id, confirmation_name)`: 소유자, 공동 장부, 이름 확인 후 연관 데이터 영구 삭제

함수 인수는 UUID·길이·정규화 규칙을 다시 확인한다. 권한 실패는 `42501`, 상태 충돌이나 만료는 기능별 안정적인 오류 코드 또는 메시지로 구분해 서버 워크플로가 사용자용 문구로 변환한다.

### 6.2 RLS

- 초대 대상은 자신의 초대를 조회할 수 있다.
- 장부 소유자는 자신이 소유한 장부의 초대를 조회할 수 있다.
- 다른 사용자와 비구성원은 초대를 조회할 수 없다.
- 초대 상태 변경과 구성원 변경은 직접 테이블 쓰기가 아니라 검증 함수만 사용한다.
- 공동 장부 구성원은 삭제되지 않은 모든 거래를 조회할 수 있다.
- 소유자는 공동 장부의 모든 거래를 수정·휴지통 이동할 수 있다.
- 일반 참여자는 자신이 만든 거래만 수정·휴지통 이동할 수 있다.
- 구성원에서 제거되는 즉시 장부, 분류, 거래, 통계 접근권한을 잃는다.

## 7. 애플리케이션 구조와 데이터 흐름

### 7.1 장부 컨텍스트

현재 `default_ledger_id` 조회 로직을 공용 장부 컨텍스트 모듈로 확장한다. 컨텍스트는 사용자 ID, 현재 장부, 역할, 참여 장부 요약 목록을 제공한다. 저장된 기본 장부가 없거나 더 이상 접근할 수 없으면 개인 장부를 찾아 복구하고 그 장부를 사용한다.

앱 셸에는 모바일과 PC에서 모두 접근 가능한 장부 선택기를 둔다. 사용자가 장부를 선택하면 서버 액션이 구성원 여부를 확인한 후 `default_ledger_id`를 갱신하고 현재 경로를 다시 렌더링한다. 선택 장부 변경은 가계부·통계·설정에 동시에 반영된다.

### 7.2 공동 장부 관리 화면

`/settings`에 다음 영역을 추가한다.

- 장부 선택 및 `공동 장부 만들기`
- 받은 초대 목록과 수락·거절 버튼
- 현재 공동 장부의 구성원 목록
- 소유자용 초대 입력, 대기 초대 취소, 구성원 제거
- 참여자용 `이 장부 나가기`
- 소유자용 `공동 장부 삭제`

개인 장부에서는 초대·나가기·삭제를 표시하지 않는다. 일반 참여자는 장부 기준일과 분류를 읽기만 할 수 있지만 공동 장부 나가기는 사용할 수 있다. 삭제 확인창은 복구 불가 안내와 정확한 장부 이름 입력을 요구한다.

### 7.3 입력자 표시

거래 조회에 작성자 프로필의 `display_name`을 포함한다. 개인 장부에서는 기존의 간결한 목록을 유지하고 공동 장부에서만 입력자를 표시한다. 작성자가 나간 뒤에도 프로필 행은 유지되므로 과거 거래의 입력자 이름은 계속 보인다.

## 8. 서버 워크플로와 오류 처리

서버 액션은 Zod로 장부명, 대상 식별자, UUID, 삭제 확인명을 검증한다. 워크플로는 인증 없음, 소유자 전용, 이미 구성원, 중복 초대, 본인 초대, 초대 만료, 접근권한 상실을 구분한다. 화면에는 내부 DB 메시지를 그대로 노출하지 않고 사용자가 조치할 수 있는 한국어 안내를 표시한다.

변경 버튼은 요청 중 비활성화해 중복 제출을 막는다. 실패 시 입력값과 현재 모달을 유지한다. 초대 수락·장부 전환·탈퇴·삭제 성공 후 앱 셸, 가계부, 통계, 설정 경로를 함께 재검증한다. 현재 장부를 잃는 변경은 개인 장부의 `/ledger`로 이동한다.

동시에 같은 초대를 수락하거나 같은 사용자를 초대해도 부분 상태가 남지 않아야 한다. 고유 인덱스와 함수 내부 행 잠금을 사용해 한 요청만 성공시키고 나머지는 이미 처리됐다는 결과로 변환한다.

## 9. 테스트 전략

### 9.1 단위 테스트

- 장부명·초대 대상·삭제 확인 검증
- 역할별 워크플로 결과와 사용자 메시지
- 장부 목록 및 초대·구성원 조회 매핑
- 기본 장부 복구와 전환 결정
- 공동 장부에서만 입력자 표시
- 모바일·PC 공용 장부 선택기와 설정 화면 권한별 버튼

### 9.2 pgTAP/RLS 테스트

- 공동 장부 생성 시 소유자와 기본 분류가 함께 생성됨
- 개인 장부 초대, 본인 초대, 중복 초대 거부
- 대상만 초대를 조회·수락·거절할 수 있음
- 7일이 지난 초대 수락 거부
- 소유자만 초대를 취소하고 구성원을 제거할 수 있음
- 참여자는 본인만 나갈 수 있고 소유자는 나갈 수 없음
- 제거·탈퇴 직후 장부 데이터 접근이 거부되고 기본 장부가 개인 장부로 복구됨
- 일반 참여자는 본인 거래만 변경하고 소유자는 전체 거래를 변경함
- 공동 장부 삭제가 관련 거래·분류·구성원·초대를 함께 삭제함

### 9.3 E2E

호스팅된 전용 개발 Supabase에서 두 계정을 사용한다.

1. 사용자 A가 공동 장부를 만든다.
2. 사용자 B를 아이디로 초대한다.
3. 사용자 B가 앱에서 수락하고 장부를 선택한다.
4. 두 사용자가 각각 거래를 추가하고 입력자 표시를 확인한다.
5. 사용자 B가 A의 거래를 수정할 수 없고 A는 두 거래를 관리할 수 있음을 확인한다.
6. 사용자 B가 나간 뒤 공동 장부 접근이 사라지고 개인 장부로 돌아가는지 확인한다.

파괴적 E2E는 기존 안전 플래그가 활성화된 전용 프로젝트에서만 실행한다. 모바일과 PC 뷰포트를 모두 검증한다.

## 10. 마이그레이션과 배포

새 마이그레이션은 `202608270005_shared_ledgers.sql`로 추가한다. 기존 운영 데이터를 삭제하거나 기존 개인 장부를 변경하지 않는다. 초대 테이블·함수·트리거·RLS 정책을 만든 뒤 pgTAP 확인 쿼리와 Supabase SQL Editor 적용 순서를 문서화한다.

앱 코드는 마이그레이션 적용 뒤 배포한다. 마이그레이션이 적용되지 않은 환경에서는 공동 장부 화면에 일반 오류를 표시하고 기존 개인 장부·거래·통계 기능은 계속 동작해야 한다.

## 11. 완료 기준

- 한 사용자가 공동 장부를 만들고 다른 가입자를 초대할 수 있다.
- 초대 대상이 수락한 뒤 양쪽에서 같은 장부와 거래를 볼 수 있다.
- 소유자·참여자 권한이 UI와 RLS 양쪽에서 일치한다.
- 장부 전환이 가계부·통계·설정 전체에 즉시 반영된다.
- 탈퇴·제거·삭제 후 접근권한과 기본 장부가 안전하게 정리된다.
- 외부 이메일과 소유권 이전 없이 첫 공동 장부 흐름이 PC와 모바일에서 완결된다.
