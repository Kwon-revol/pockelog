# PockeLog 거래 가계부 설계

## 1. 목적과 범위

이번 수직 기능은 로그인 사용자가 자신의 기본 장부에서 수입·지출 거래를 등록하고, 선택 기간의 목록과 합계를 조회하며, 기존 거래를 수정하거나 휴지통으로 이동할 수 있게 한다.

포함 범위:

- 거래 등록, 조회, 검색, 필터, 정렬, 수정, 휴지통 이동
- 현재 정산 기간 및 직접 선택 기간의 총수입·총지출·잔액
- 모바일 카드 목록과 하단 고정 추가 버튼
- PC 표 목록과 상단 추가 버튼
- PC·모바일 공통 무한 스크롤
- 거래 유형에 맞는 활성 분류 선택
- 운영 Supabase에 별도로 적용할 두 번째 마이그레이션

이번 범위에서 제외한다:

- 휴지통 전용 화면, 복원, 영구 삭제
- 통계 탭의 월별·분류별 상세 화면
- 분류 생성·수정·비활성화 UI
- 공동 장부 생성·초대 UI
- CSV 내보내기와 반복 거래
- 비밀번호 찾기 기능 수정

## 2. 구현 방식

Next.js 서버 컴포넌트가 최초 장부·분류·거래·요약을 읽고, 서버 액션이 거래 등록·수정·휴지통 이동을 처리한다. 브라우저는 서비스 역할 키를 사용하지 않으며 로그인 사용자의 Supabase 세션과 RLS를 그대로 사용한다.

목록의 추가 페이지는 Route Handler를 통해 같은 사용자 세션으로 조회한다. 무한 스크롤 클라이언트는 IntersectionObserver로 목록 끝 감지 지점을 관찰하고 다음 커서를 요청한다. 첫 50건은 서버 렌더링하고 이후 50건씩 추가한다.

기간 합계는 `security invoker` SQL RPC가 삭제되지 않은 거래만 집계한다. 거래 저장 후 `/ledger` 서버 데이터를 다시 검증하고 화면을 갱신한다.

## 3. 데이터베이스

초기 마이그레이션은 운영 프로젝트에 이미 적용되었으므로 수정하지 않는다. 새 파일 `supabase/migrations/202608260002_transactions.sql`을 추가한다.

### 3.1 `public.transactions`

| 열 | 형식 | 규칙 |
|---|---|---|
| `id` | `uuid` | 기본값 `gen_random_uuid()`, PK |
| `ledger_id` | `uuid` | `ledgers(id)` 참조, 필수 |
| `type` | `transaction_type` | `income` 또는 `expense` |
| `occurred_on` | `date` | 필수 |
| `description` | `text` | trim 후 1~100자 |
| `amount` | `bigint` | 1 이상 |
| `category_id` | `uuid` | `categories(id)` 참조, 필수 |
| `memo` | `text` | nullable, 최대 500자 |
| `created_by` | `uuid` | `auth.users(id)` 참조, 필수 |
| `idempotency_key` | `uuid` | 저장 시도별 키, 필수 |
| `created_at` | `timestamptz` | UTC 생성 시각 |
| `updated_at` | `timestamptz` | UTC 수정 시각 |
| `deleted_at` | `timestamptz` | nullable, 휴지통 이동 시 기록 |
| `deleted_by` | `uuid` | nullable, `auth.users(id)` 참조 |

`(ledger_id, idempotency_key)`는 고유하다. 일반 목록 조회용 `(ledger_id, occurred_on desc, created_at desc, id desc) where deleted_at is null` 인덱스를 둔다.

### 3.2 데이터 무결성

`before insert or update` 트리거는 다음을 검사한다.

- 선택 분류가 거래와 같은 장부에 속함
- 선택 분류 유형이 거래 유형과 같음
- 새 거래에는 활성 분류만 사용함
- `created_by`는 생성 시 `auth.uid()`와 같음
- 휴지통 상태는 `deleted_at`과 `deleted_by`가 함께 null이거나 함께 값이 있음

기존 거래 수정 시 해당 분류가 비활성화되었더라도 분류를 바꾸지 않는 수정은 허용한다. 유형 또는 분류를 바꾸면 새 조합은 활성 분류여야 한다.

### 3.3 RLS

- 장부 구성원은 삭제되지 않은 일반 거래를 조회할 수 있다.
- 장부 소유자는 장부의 모든 일반 거래를 수정하고 휴지통으로 이동할 수 있다.
- 일반 구성원은 자신이 만든 일반 거래만 수정하고 휴지통으로 이동할 수 있다.
- 거래 생성자는 `created_by = auth.uid()`이고 해당 장부 구성원이어야 한다.
- 휴지통 거래 조회, 복원, 영구 삭제 정책은 후속 휴지통 기능에서 별도 추가한다. 현재 일반 조회 정책은 `deleted_at is null`만 허용한다.
- `created_by`, `ledger_id`, `created_at`은 일반 클라이언트가 수정할 수 없다.

### 3.4 기간 요약 RPC

`public.get_transaction_summary(target_ledger_id uuid, start_on date, end_exclusive date)`는 `security invoker`로 동작한다.

- `start_on <= occurred_on < end_exclusive`
- `deleted_at is null`
- 총수입은 `income` 합계
- 총지출은 `expense` 합계
- 잔액은 총수입 - 총지출
- 결과가 없으면 세 값 모두 0

## 4. 기간 계산

기본 범위는 장부의 `period_start_day`를 사용한다. 현재 값 `1`이면 현재 달 1일부터 다음 달 1일 미만이다. 2~28이면 해당 시작일부터 다음 달 같은 시작일 미만이며, `null`은 각 달의 말일부터 다음 달 말일 미만이다.

화면의 종료일 입력은 포함 날짜로 보여주고 서버 쿼리는 종료일 다음 날을 `end_exclusive`로 사용한다. 날짜 계산은 순수 함수로 분리해 윤년, 월말, 연도 경계를 단위 테스트한다.

## 5. 서버 인터페이스

### 5.1 거래 조회

`getLedgerPageData(searchParams)`는 현재 사용자와 기본 장부를 확인한 뒤 다음을 반환한다.

- 장부명과 정산 기준일
- 활성 분류 목록
- 정규화된 조회 기간과 필터
- 첫 거래 페이지 50건
- 다음 커서
- 기간 요약

추가 페이지 API는 `GET /api/transactions`를 사용한다. 입력은 장부 ID를 직접 신뢰하지 않고 현재 사용자의 기본 장부와 일치하는지 확인한다.

커서는 마지막 행의 `occurred_on`, `created_at`, `id`를 URL-safe 값으로 인코딩한다. 동일 날짜·동일 생성 시각에서도 `id`를 마지막 정렬 키로 사용해 중복과 누락을 막는다.

필터:

- 시작일과 종료일
- 내용·메모 검색어, 최대 100자
- `income`, `expense`, 전체
- 분류 ID 또는 전체
- 최신순 또는 오래된순

### 5.2 서버 액션

- `createTransactionAction(previousState, formData)`
- `updateTransactionAction(previousState, formData)`
- `trashTransactionAction(transactionId)`

모든 액션은 Zod 검증 후 사용자 세션 Supabase 클라이언트로 실행한다. 성공 시 `/ledger`를 재검증하고 성공 결과를 반환한다. 멱등성 키 충돌은 같은 저장 시도의 재전송으로 취급하며 중복 행을 만들지 않는다.

## 6. 화면 설계

### 6.1 상단

- 현재 조회 기간 시작일·종료일
- 총수입, 총지출, 잔액 카드
- 검색, 유형, 분류, 정렬 필터
- PC `내역 추가` 버튼

필터 상태는 URL 검색 파라미터에 저장하여 새로고침과 공유 시 같은 조회 상태를 유지한다.

### 6.2 거래 목록

- 모바일: 거래일별 제목 아래 카드 목록
- PC: 날짜, 내용, 분류, 유형, 금액 열을 가진 표
- 행 또는 카드를 선택하면 수정 폼 열기
- 첫 50건 이후 목록 끝 감지 지점이 보이면 다음 50건 자동 요청
- 요청 중 목록 하단 로딩 표시
- 요청 실패 시 자동 재요청을 멈추고 `다시 시도` 표시
- 마지막 페이지에 도달하면 감시만 중단하고 별도의 완료 문구를 표시하지 않음
- 검색·필터·기간·정렬 변경 시 누적 목록과 커서를 초기화

### 6.3 추가·수정 폼

- 모바일: 화면 아래에서 올라오는 패널
- PC: 우측 패널
- 필드: 수입/지출, 거래일, 내용, 분류, 금액, 선택 메모
- 신규 거래일 기본값은 `Asia/Seoul` 기준 오늘
- 유형을 변경하면 해당 유형의 활성 분류만 표시하고 기존 분류 선택을 초기화
- 금액 입력은 숫자만 저장하며 화면에는 천 단위 구분 표시
- 제출 중 저장 버튼 잠금
- 오류 시 폼 값과 패널 유지

### 6.4 휴지통 이동

수정 폼에서 `삭제`를 선택하면 확인 대화상자를 표시한다. 확인 후 `deleted_at`과 `deleted_by`를 기록하고 일반 목록과 합계에서 즉시 제외한다. 복원과 영구 삭제는 이번 화면에 제공하지 않는다.

## 7. 오류와 빈 상태

- 거래가 없으면 첫 거래 추가 안내를 표시한다.
- 세션이 없으면 현재 URL을 보존해 로그인으로 이동한다.
- 잘못된 날짜·금액·분류는 필드별 한국어 오류를 표시한다.
- 권한 또는 사라진 거래 오류는 `이 내역을 변경할 수 없습니다.`로 통일한다.
- 네트워크 오류는 입력을 유지하고 재시도 안내를 표시한다.
- 추가 페이지 오류는 기존 목록을 보존한다.

## 8. 테스트와 검증

### 단위·컴포넌트

- 정산 시작일 1~28, 말일, 윤년, 연도 경계
- 폼 trim, 금액 정수, 날짜, 메모 길이, 유형·분류 입력 검증
- 수입·지출·잔액 계산 결과 표시
- 유형 변경 시 분류 선택 초기화
- 무한 스크롤 중복 호출 방지, 커서 누적, 필터 변경 초기화, 끝 도달 시 조용히 중단

### DB 계약

- 거래 장부와 분류 장부 불일치 거부
- 거래 유형과 분류 유형 불일치 거부
- 멱등성 키 중복 방지
- 타인 개인 장부 거래 조회 차단
- 장부 소유자 거래 CRUD 허용
- 일반 구성원은 본인 거래만 수정 가능
- 휴지통 거래가 일반 조회와 요약에서 제외됨

### E2E

- 가입된 사용자 로그인 → 첫 지출 추가 → 합계와 목록 확인
- 수입 추가 → 잔액 확인
- 거래 수정 → 목록과 합계 갱신
- 거래 휴지통 이동 → 목록과 합계에서 제외
- PC 표와 모바일 카드·고정 추가 버튼 확인
- 50건을 넘는 테스트 데이터에서 자동 다음 페이지 조회

## 9. 배포 순서

1. 두 번째 SQL 마이그레이션을 운영 Supabase SQL Editor에서 한 번 실행한다.
2. 애플리케이션 코드를 GitHub 기능 브랜치에 push하고 PR 검사를 통과시킨다.
3. `main` 병합 후 Vercel 운영 배포를 확인한다.
4. 실제 계정으로 거래 추가·수정·휴지통 이동과 기간 합계를 확인한다.

마이그레이션이 적용되기 전에 새 애플리케이션 코드를 운영에 병합하지 않는다.
