# PockeLog 계정·프로필 설정 설계

- 문서 상태: 사용자 승인 설계안
- 작성일: 2026-09-02
- 대상: 설정 화면의 본인 프로필 및 비밀번호 변경

## 1. 목표

로그인 사용자가 현재 선택한 장부나 장부 역할과 관계없이 자신의 사용자명과 전화번호를 확인·수정하고, 가입 이메일을 확인하며, 현재 비밀번호 검증 후 새 비밀번호로 변경할 수 있게 한다.

공동 장부 소유자와 일반 구성원은 모두 본인의 프로필만 수정할 수 있다. 소유자가 구성원의 프로필을 수정하거나 구성원이 소유자·다른 구성원의 프로필을 수정하는 기능은 제공하지 않는다.

## 2. 범위

### 포함

- 설정 화면 상단의 `내 프로필` 영역
- 로그인 사용자 본인의 사용자명·전화번호 조회 및 수정
- 가입 이메일 읽기 전용 표시
- 현재 비밀번호 확인 후 새 비밀번호 변경
- 비밀번호 변경 성공 후 모든 기기의 세션 종료 및 로그인 화면 이동
- 모바일·PC 반응형 화면
- 입력 검증, RLS·권한 검증, 단위·통합·E2E 테스트
- Supabase 적용 및 운영 확인 문서

### 제외

- 이메일 변경
- 로그인 아이디 변경
- 회원 탈퇴
- 관리자가 다른 사용자의 프로필을 수정하는 기능
- 별도의 `모든 기기에서 로그아웃` 버튼
- 프로필 이미지

## 3. 화면 구성

설정 화면의 제목 아래, 장부 설정보다 위에 `내 프로필` 카드를 둔다. 이 카드는 현재 장부가 개인 장부인지 공동 장부인지, 사용자가 소유자인지 일반 구성원인지와 관계없이 표시한다.

프로필 카드에는 다음 필드를 표시한다.

- 사용자명: 편집 가능, 1~30자, 앞뒤 공백 제거
- 전화번호: 편집 가능, 숫자와 하이픈 입력 허용, 저장 전 숫자만 남김
- 가입 이메일: 읽기 전용

프로필 카드 아래에 별도 `비밀번호 변경` 카드를 둔다.

- 현재 비밀번호
- 새 비밀번호
- 새 비밀번호 확인
- `비밀번호 변경` 버튼

비밀번호 변경 카드에는 성공 시 모든 기기에서 로그아웃되고 다시 로그인해야 한다는 안내를 항상 표시한다. 별도의 전체 로그아웃 버튼은 추가하지 않는다. 기존 `로그아웃` 버튼은 현재 기기 세션만 종료하는 기능으로 유지한다.

## 4. 데이터와 권한

기존 테이블을 사용한다.

- `public.profiles.display_name`: 사용자명
- `public.user_private_profiles.phone_normalized`: 전화번호
- `auth.users.email`: 읽기 전용 이메일

기존 RLS와 열 단위 grant는 본인 프로필 수정만 허용한다. 추가 마이그레이션은 사용자명과 전화번호를 한 트랜잭션으로 갱신하는 `public.update_my_profile(text,text)` 함수를 추가한다.

함수는 다음 규칙을 따른다.

- `auth.uid()`가 없으면 실패한다.
- 입력 사용자 ID를 받지 않는다.
- `auth.uid()`와 일치하는 `profiles.id`, `user_private_profiles.user_id`만 변경한다.
- 사용자명은 `btrim` 후 1~30자여야 한다.
- 전화번호는 숫자만 허용하고 비어 있을 수 없다.
- 두 테이블 중 하나라도 변경되지 않으면 전체 작업을 실패시킨다.
- `security invoker`와 빈 `search_path`를 사용하고 모든 객체명을 완전 수식한다.
- `authenticated`만 실행할 수 있고 `anon`, `PUBLIC` 실행 권한은 제거한다.

일반 구성원 B가 공동 장부를 선택한 상태에서도 B의 프로필만 변경된다. 장부 소유자 A의 프로필이나 다른 구성원의 프로필은 변경할 수 없다.

## 5. 서버 구조

프로필 설정은 장부 설정 코드와 파일을 분리한다.

- 프로필 타입과 입력 스키마
- 프로필 조회
- Supabase 프로필 게이트웨이
- 프로필 수정·비밀번호 변경 워크플로
- 서버 액션
- 프로필 및 비밀번호 폼

설정 페이지 조회 시 기존 장부 설정·공동 장부 데이터와 함께 로그인 사용자의 프로필을 조회한다. 프로필 조회 실패는 장부 설정 데이터와 구분되는 안전한 오류 상태로 처리하며 이메일·전화번호·내부 사용자 ID를 오류 메시지나 로그에 포함하지 않는다.

프로필 저장 성공 후 다음 경로를 다시 검증한다.

- `/settings`
- `/ledger`
- `/statistics`
- `/settings/trash`

공동 장부 거래의 입력자 표시 이름은 다음 조회에서 변경된 사용자명을 사용한다.

## 6. 비밀번호 변경 흐름

1. 서버가 현재 세션 사용자를 확인한다.
2. 현재 세션의 이메일과 사용자가 입력한 현재 비밀번호로 `signInWithPassword`를 호출한다.
3. 검증이 실패하면 `현재 비밀번호를 확인해 주세요.`라는 동일한 메시지를 반환하고 새 비밀번호를 변경하지 않는다.
4. 새 비밀번호는 최소 8자이며 확인 값과 일치해야 한다.
5. 검증 성공 후 `updateUser({ password })`로 비밀번호를 변경한다.
6. 변경 성공 후 `signOut({ scope: "global" })`로 모든 기기 세션을 종료한다.
7. `/login?passwordChanged=1`로 이동하고 로그인 화면에 `비밀번호가 변경됐습니다. 새 비밀번호로 다시 로그인해 주세요.`를 표시한다.

클라이언트가 이메일이나 사용자 ID를 전달하지 않는다. 서버가 검증한 현재 세션 값만 사용한다. 현재 비밀번호, 새 비밀번호, 인증 토큰은 로그에 기록하지 않는다.

비밀번호 검증 성공 후 비밀번호 변경 자체가 실패하면 로그아웃하지 않고 재시도 안내를 표시한다. 비밀번호 변경 성공 후 전체 로그아웃 호출에서 공급자 오류가 발생하더라도 현재 응답의 인증 쿠키를 제거해 이 기기에서는 로그인 화면으로 이동하도록 한다.

## 7. 입력 검증과 오류 처리

- 사용자명: 필수, 앞뒤 공백 제거, 1~30자
- 전화번호: 필수, 숫자와 하이픈만 입력, 저장 시 숫자만 유지
- 현재 비밀번호: 필수
- 새 비밀번호: 최소 8자
- 새 비밀번호 확인: 새 비밀번호와 일치

프로필 저장은 성공·입력 오류·세션 만료·일시적 서버 오류를 구분한다. 세션 만료는 `/login?next=%2Fsettings`로 이동한다. RLS·DB 내부 오류 문구는 사용자에게 노출하지 않는다.

저장 중에는 해당 폼의 버튼과 입력을 비활성화한다. 프로필 폼과 비밀번호 폼의 상태는 분리하여 한쪽 오류가 다른 폼의 입력이나 메시지를 지우지 않게 한다.

## 8. 테스트

### 단위 테스트

- 사용자명 trim·길이 검증
- 전화번호 숫자 정규화와 잘못된 문자 거부
- 새 비밀번호 불일치·길이 검증
- 프로필 RPC 결과와 안전한 오류 매핑
- 현재 비밀번호가 틀리면 `updateUser`를 호출하지 않음
- 비밀번호 변경 성공 시 전역 로그아웃과 로그인 이동
- 프로필·비밀번호 폼의 성공·오류·대기 상태
- 공동 장부 일반 구성원에게도 `내 프로필`이 표시됨

### 데이터베이스 테스트

- 본인 사용자명·전화번호 동시 변경 성공
- 다른 사용자 행 변경 불가
- 사용자 ID를 인자로 받지 않음
- 비로그인 실행 거부
- `PUBLIC`, `anon` 실행 권한 없음
- 빈 `search_path`, invoker 권한, 완전 수식 객체 확인

### E2E

전용 개발 Supabase의 안전 가드 아래에서 PC·모바일 모두 확인한다.

1. 가입 후 설정에서 본인 이메일·사용자명·전화번호 확인
2. 사용자명·전화번호 변경 후 새로고침해 유지 확인
3. 공동 장부 일반 구성원 상태에서도 본인 프로필 수정 확인
4. 잘못된 현재 비밀번호로 변경 거부 확인
5. 올바른 현재 비밀번호로 변경 후 로그인 화면 이동 확인
6. 이전 비밀번호 로그인 실패와 새 비밀번호 로그인 성공 확인

운영 Supabase를 자동 파괴 테스트 대상으로 사용하지 않는다.

## 9. 배포 순서

1. 전용 개발 Supabase에서 프로필 마이그레이션과 DB 계약 테스트를 실행한다.
2. 앱 단위 테스트, 타입 검사, 린트, 빌드, PC·모바일 E2E를 통과시킨다.
3. 운영 Supabase SQL Editor에서 새 프로필 마이그레이션을 한 번 실행한다.
4. 확인 쿼리로 함수와 실행 권한을 확인한다.
5. 앱 코드를 `main`에 배포한다.
6. 본인 프로필 수정과 비밀번호 변경 후 재로그인을 수동 확인한다.
